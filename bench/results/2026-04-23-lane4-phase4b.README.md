## What this proves — and what it doesn't

Phase 4b (WAL append-on-write) is architecturally correct and landed green:

- `tests/cross-build/phase4b.json` — 6/6 fixture cases pass on both C and Rust
  builds (single-commit frame emission, multi-commit recovery on reopen, WAL
  absent after checkpoint, growing dirty set, uncommitted-tail discard,
  empty-session no-WAL-on-close).
- `spec/wal.spec.md` now carries the full Phase 4b protocol: session
  activation contract, pager dirty-set semantics, snapshot-diff v1
  implementation, multi-frame recovery rule. Spec is language-neutral.
- File-format roundtrip matrix remains 108/108 (no regression).

But **the lane 4 number did not move**, and the reason is worth naming:

### Why Phase 4b didn't move lane 4

The workload (`bench/lanes/04-insert-throughput/workload.sql`) is:

```
PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL;
CREATE TABLE t (id INTEGER PRIMARY KEY, payload TEXT);
BEGIN;
INSERT INTO t (id, payload) VALUES (0, '...');
...
INSERT INTO t (id, payload) VALUES (99999, '...');
COMMIT;
```

A single `BEGIN` / `COMMIT` around 100 000 INSERTs. In Phase 4b's
snapshot-diff implementation that is **one commit** — one pass over the
final image, one batch of dirty-page frames, one fsync. Cost ≈ cost of
Phase 3d's single atomic-rename path. There is no win to extract because
the workload isn't exercising the thing Phase 4b makes cheaper.

Phase 4b's actual unlock is **many small commits**: the canonical OLTP
shape where each INSERT (or each small batch of them) is its own
transaction. In that shape, Phase 3d would rewrite the entire image on
every commit, whereas Phase 4b appends just the dirty pages. A
1 000-commit × 100-row-per-commit workload would show the curve.

Leap's 20 k ins/s leap-c, 37 k ins/s leap-rust numbers on lane 4 are
**VDBE CPU cost** on the insert loop, not disk I/O. The VDBE dispatch
tuning that mainline has accumulated over 20+ years is the gap, not the
WAL path. Phase 4b is necessary scaffolding for future wins but not the
win itself on this workload.

### Honest framing for publication

- **Lane 4 is not a Phase 4b win.** It remains a wide loss vs mainline
  (~34× on leap-c, ~18× on leap-rust). That's the same honest loss the
  2026-04-20 validated CSV disclosed.
- **Phase 4b is a correctness milestone, not a benchmark milestone.** It
  brings leap to parity with mainline's *architecture* for write-ahead
  logging: incremental per-commit frame emission, checkpointed on close,
  fsync boundaries. Lane 4 as currently authored doesn't measure that
  axis.
- **Follow-up sub-lane (out of scope for this session):** a lane 4b with
  N-small-commits workload would demonstrate the architectural win and
  is the right place for Phase 4b benchmark claims.

### Claim retraction

The pre-Phase-4b framing in `SCOPE.md` and `DASHBOARD.md` treated Phase
4b as "the actual lane 4 unlock." That framing was wrong: the blocker on
lane 4 is not the WAL write-path but the harness workload shape. Phase
4b does fix the structural gap on the *architecture* axis; it does not
fix the number on the existing single-transaction workload. Dashboard
reflects this honestly as of 2026-04-23.
