# Benchmark lanes — language-neutral spec

## Why this exists

sqlite-leap's public commitment is: beat mainline SQLite on all six benchmark lanes; match or beat Turso on every lane. Without a precisely-specified harness for each lane, the commitment is unfalsifiable. This spec defines each lane as a reproducible experiment: inputs, measurement method, comparator baselines, publication format.

## Shared conventions

### Platforms

- **Publication platform**: Linux x86_64, Ubuntu 24.04, kernel ≥ 6.8. Specific hardware profile recorded in the publication artifact (see `tools/bench-profile.md` for the canonical profile).
- **Informational platform**: macOS arm64 (Apple Silicon). Numbers recorded alongside Linux but not headline-published — macOS hardware varies too much for cross-machine comparison.

### Statistics

Every lane reports:

- **Median** of N runs (N ≥ 30).
- **p95** of N runs.
- **min / max** for diagnostic purposes.

Warm-up: 5 runs before measurement begins; their values are discarded. Runs execute back-to-back with no sleep between (we measure the engine, not the scheduler).

Single-run outlier rejection: results > 3× the median are re-run up to 3 times; if persistent, they are published as-is (they are real signal).

### Baselines

- **Mainline SQLite**: version pinned in `bench/baselines.json`. Bump rule: at every minor-version release of mainline. Each bump is a separate bench run that records the before/after on all 6 lanes.
- **Turso**: version pinned in `bench/baselines.json`. Same bump rule.
- **Self-regression**: the prior leap run's numbers, for regression detection.

### Output artifact

Each bench publication produces:

```
bench/results/<YYYY-MM-DD>-<git-sha>/
├── summary.md             # human-readable
├── raw.csv                # every individual measurement
├── medians.json           # per-lane median + p95 + min/max
├── plots/                 # one .png per lane, time-series over recent runs
└── environment.json       # platform, toolchain, hardware profile
```

## Lane 1 — Cold start

### Metric

Time from the first process-level syscall of the engine binary to the moment the engine is ready to accept the first query.

### Harness

A minimal binary that:

1. Records `t0` = `clock_gettime(CLOCK_MONOTONIC_RAW)` at the first line of `main`.
2. Opens a pre-existing database file (path passed as argv[1]).
3. Parses + compiles a trivial query (`SELECT 1`) — up to but not including execution of the first VDBE instruction.
4. Records `t1`.
5. Prints `(t1 - t0)` in nanoseconds and exits.

### Inputs

- **Empty DB**: a freshly-created 1-page file.
- **Small DB**: 1 table, 100 rows, 3 indexes.
- **Wide schema DB**: 500 tables, 50 columns each. This is where mainline SQLite historically suffers — `sqlite_schema` replay balloons cold-start latency.

### Comparators

- Mainline `sqlite3` CLI run against the same three DBs, instrumented identically (patch `.open` path to record the two timestamps).
- Turso binary run identically.

### Targets (from CLAUDE.md)

- Empty/small DB: ≥ 4× faster than mainline; ≤ Turso.
- Wide schema DB: order-of-magnitude faster than mainline (mainline spends seconds here).

## Lane 2 — Parse speed

### Metric

Time to parse N SQL statements end-to-end (tokenizer + grammar + AST), averaged per statement.

### Harness

Reads a file of newline-separated SQL statements; for each statement, times parse-only (no compile, no execute); sums and divides by N.

### Inputs

- **select-heavy** corpus: 10k `SELECT ... FROM ... WHERE ... ORDER BY` statements, varied.
- **dml** corpus: 10k `INSERT / UPDATE / DELETE` statements, varied.
- **ddl** corpus: 10k `CREATE TABLE / CREATE INDEX / ALTER` statements.
- **pathological** corpus: 1k statements with extreme parenthesization, long identifier names, 1000-column lists. Tests the parser's robustness, not just its speed.

### Comparators

Mainline SQLite's `sqlite3_prepare_v2` run on the same corpus. Turso equivalent.

### Targets

Beat mainline's Lemon-generated parser by a measurable margin. Exact figure TBD after first profile; the grammar is table-driven in our spec, so a generated DFA plus arena-allocated AST should give us a structural advantage.

## Lane 3 — In-memory SELECT

### Metric

Throughput (rows/sec) of a streaming SELECT over a pre-populated in-memory table.

### Harness

1. Open `:memory:` DB.
2. Run `CREATE TABLE t (a INTEGER, b INTEGER, c TEXT, d REAL)`.
3. `INSERT` 1M rows (values generated by a seeded PRNG for reproducibility).
4. Record `t0`.
5. Run `SELECT * FROM t` and drain all rows (consuming each row into a volatile sink to prevent DCE).
6. Record `t1`. Report `1M / (t1 - t0)` rows/sec.

Variants:

- **Full scan** (above).
- **Projection**: `SELECT a FROM t` (single integer column).
- **Filtered**: `SELECT * FROM t WHERE a > 500000` (50% of rows).
- **Aggregated**: `SELECT SUM(a), COUNT(*) FROM t`.
- **Ordered**: `SELECT * FROM t ORDER BY a DESC LIMIT 100`.

### Comparators

Mainline, Turso.

### Targets

Beat Turso (they are ~20% faster than mainline). We close the gap via tighter VDBE dispatch + arena-based row allocation.

## Lane 4 — INSERT throughput (WAL, single writer)

### Metric

Throughput (rows/sec) of a sustained `INSERT` load inside a single transaction, with WAL in active durable mode.

### Harness

1. Open DB with `PRAGMA journal_mode=WAL` (once WAL write-side lands per Phase 4b).
2. `CREATE TABLE t (a, b, c)`.
3. `BEGIN`.
4. Loop: `INSERT INTO t VALUES (?, ?, ?)` bound to PRNG-derived values, for 1M iterations.
5. `COMMIT`.
6. Report `1M / elapsed` rows/sec.

Variants:

- **No-index table** (above).
- **3-index table** (b-tree indexes on a, b, c).
- **Bulk `INSERT ... VALUES (...), (...), ...`** (batches of 1000 tuples per statement).

### Comparators

Mainline, Turso. Turso's async io_uring path is what we are chasing here.

### Target

≥ Turso on all variants on Linux. (macOS numbers informational only.)

### Gating phase

Requires Phase 4b (WAL write) + Phase 5b (io_uring) complete. Until both phases ship, this lane runs against mainline and Turso as a baseline-capture exercise but doesn't measure leap.

## Lane 5 — Binary size

### Metric

On-disk size of the compiled engine binary, core-only (no extensions, no CLI ornaments).

### Harness

Compile the engine as a static library (archive of `.o` for C, `staticlib` crate for Rust), stripped of debug symbols. Measure bytes via `stat`. Record under:

- `core-c.a` (C, stripped, no shell)
- `core-rust.rlib` (Rust staticlib)
- `core-wasm.wasm` (wasm-opt -O3)

### Comparators

Mainline: `sqlite3.c` amalgamation compiled `-Os -DSQLITE_OMIT_LOAD_EXTENSION` (no shell). Turso: equivalent rustc minimal configuration.

### Targets

- C: beat mainline (mainline is ~600KB; we target < 550KB at v1-feature parity).
- Rust: narrow the Rust-overhead gap; target ≤ 1.5× the C number.
- WASM: beat `sql.js` and `sqlite-wasm` (both ship > 1 MB).

## Lane 6 — Memory footprint

### Metric

RSS at "idle" — one `:memory:` DB open with 1 small table, waiting for input.

### Harness

1. Spawn the engine binary.
2. Open `:memory:`, create `t (a, b, c)`, insert 10 rows, commit.
3. Enter a read-idle state (block on stdin).
4. External observer reads `/proc/<pid>/status`'s `VmRSS` (Linux) or `ps -o rss` (macOS).
5. Record.

### Comparators

Mainline CLI in same state, Turso CLI in same state.

### Targets

Beat mainline. Specific target TBD after first profile; our advantage is arena-allocated ASTs and VDBE state (no heap fragmentation), so the gap should be measurable.

## Cross-build equivalence

In addition to each lane being published as its own number, a cross-build delta report shows the C and Rust builds side by side on every lane. The hard constraint is that neither build is more than 2× slower than the other on any lane. Soft constraint: we publish per-lane "C-vs-Rust ratio" as a credibility marker — a wide gap suggests one generator is carrying unnecessary weight.

## Publication etiquette

The six lane numbers are what we beat SQLite on. Publication rules:

1. **Always publish raw CSV** alongside medians. Every data point reviewable.
2. **Always publish comparator versions** — "v3.46.0 mainline", "turso v0.1.2-commit-xyz".
3. **Always publish hardware profile** — CPU model, core count, memory speed, kernel version.
4. **Never publish a lane without its p95**. Median-only plots mislead.
5. **If we regress on any lane**, disclose it in the release post. The stunt's credibility depends on symmetric disclosure.

## Non-goals

- Micro-benchmarks (per-opcode dispatch cost, per-page I/O latency). Valuable for internal tuning; NOT part of the public six.
- Concurrency throughput. Phase 4c would add this; not in v1 public commitments.
- TPC-class benchmarks (TPC-H, TPC-C). Out of scope for a storage-engine stunt; those are SQL-engine-over-storage-engine benches, different claim.
